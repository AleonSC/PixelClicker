# Pixel Clicker – project notes

3D incremental clicker in Unity (C#, TextMeshPro). All code lives in `Assets/Scripts/`. Everything UI is built at runtime (no prefabs/scene UI required). Nothing has been compiled or run by Claude – the user tests in Unity.

## The game at a glance (full index: `docs/Index.md`)
- **Core loop:** click the cube's block -> its currency + a HUSK drops (material, never currency); blocks roll from unlocked tiers (`PixelClicker` + partials, `PixelBlockCatalog` cards/tags, `PixelLooks` 3D looks, `PixelBlockRules` special / hold blocks). Tough blocks, hazards, fillers, rare drops.
- **Progression:** Shop (packs, upgrades, Operation, consumables), Skills (Standard tree: Block Hold, Power Click, Next up, Shuffle; gathering skills Woodcutting / Foraging / Fishing, dev Mining / Farming / Electrician / Firemaking; Mastery, perks, level-up popups), Crafting, Bank, Time Stop, Combo, Auto Clicker, UFO Helper, offline progress, achievements, stats.
- **Husk economy / machines:** Husk Crush (right-click a husk for XP), sockets + couplings (`PixelSockets`, `PixelCoupling`: the one way belts / hoses connect), Recycler (streak XP) + Sorting Hopper, Storage Crate, Quantum Organizer, Funnel, Magnet, Fan, Vacuum, Sorters, Sprinkler, attuned devices, zone effects (Sap, Mold, Nuclear, gravity well via `PixelHuskQuery`); tester factory (conveyors, kiln, elevator, splitter, belt sorter, hose, trash can, robot, vacuum cleaner).
- **Minigames:** takeover and side games (Black Hole, Ghost, Meteor, Stardust, Evil Tree, Snake, Sorting Race, Dash, Traffic, Evade, Blink, Breakout, Bomb, Ultra Holes, Weak Spots), limited by `PixelMinigameLimits`.
- **Characters:** Cubie (guide / shopkeeper, tutorials), visitors (Tinkerer, Wizard, Entrepreneur, Farmer, Prospector, Lumberjack, cats Egg / Bean), pets (outfits, studio).
- **Rares and shows:** Dragon Cubes + wish, God Cubes, Prime Cubes + Gauntlet / Cubelette, Golden Snitch, Treasure, Collection Log + gallery.
- **World and camera:** floors, skies, day / night, filters, flat view, orbit / zoom / top-down / first person / free cam, view bounds.
- **UI:** code-built (`PixelUIKit`), HUD bars, Inventory, Log / event log, Toggles, Pocket, tooltips, Pixel Guide, Database, notices / tips / Did you know, pause menu (settings, save / load, guide), title screen.
- **Shared foundations:** `PixelSystems` (system list), `PixelFind`, `PixelPrefs`, `PixelStatics`, `PixelCalm`, `PixelHuskQuery`, `PixelRightClick` (who owns a right click), `PixelHuskHolder` (container steps), `PixelHuskTicker`, `PixelPointerClaim`, `PixelCarryHandles`, `PixelInstantItems`, `PixelTierPicture`, `PixelAudio` (+ code-made synths), save system.
- **Dev tools (Dev Hub, F9):** widgets / cheats, Docs (to-do, changelog, notes), Tester, Inspector, Look Studio, Setups, Events, Sounds, Console, snapshots, balance report, session recorder, crash logs.

## Data model
- `PixelTier`: name, colour/`UIColor`, `PixelType` enum (see PixelClicker.cs; values are only ever appended so saves stay valid), `TierUnlockMode` (PreviousTierThreshold / ShopOnly), `spawnWeight`, `randomPayout` + `payoutMin/Max` (a random whole amount per harvest, e.g. Electric 1-15; `amountPerClick` = the average for estimates; migrated by `packDataVersion` 3), `clicksToCollect` (tough pixels: only the last click pays; `PixelClicker.PixelHit` event for the others), `startingAmount`, `translucent` / `materialOverride`, `glow` + `glowIntensity` (emission on a runtime material copy + point light), `vacuum` flag, `spawnSwitch` (Auto = Glass, Luminescent and the `IsSpecialType` types get a spawn toggle in the Toggles window, see `PixelTier.CanSwitchOff`; `spawnDisabled` saved; `CanSpawn` used by `PickSpawnTier`), `flyAway`/`flyDirection`/`flySpeed` (old pixel streaks away in a straight camera-relative line with a smooth tapered trail instead of falling - Meteor; `flyRandomDirection` + `flyAngleRange` 10-170 deg = a random direction on the top half of the screen), `count`, `totalCollected`, `unlocked`.
- Every pixel type has a CARD in `PixelBlockCatalog.cs` (tags = what kind of block it is, Pixel Guide text, old-pixel text, borrowed sounds / effects): give a new pixel type its card there.
- Spawn: weighted random among **unlocked** tiers only (`PickSpawnTier`).
- Tough pixels raise `PixelHit` for hits 1..n-1 and `PixelFinalHit` (UI shows 'n/n', then the payout popup follows after `toughPayoutDelay`) on the breaking click. Click flow (`CollectInternal(bool automatic)`): `AddCurrency` → `PixelCollected` event → click effects → `Vacuum()` if vacuum tier → `SpawnFallingCopy` → roll next tier → `Materialize`.
- Events: `CurrencyChanged`, `CurrencyGained`, `PixelCollected(tier, amount, automatic)`, `PixelsVacuumed(vacuumTier, total, count)`, `VacuumBreakdown(double[] perTier)`.
- Shop reward tiers are added to `PixelClicker` at runtime via `EnsureTier` (locked until bought). `EnsureTier` inserts new shop tiers before the Dragon Cubes (rare drops stay at the END of the tier list). `EnsureTier` and Awake must only **raise** `Count`, never wipe typed starting values.
- `PixelShop.EnsureDefaultPacks()` (called from `Awake` and editor-only `OnValidate` via `delayCall`) walks the `BuiltInPacks` table and inserts any missing built-in pack into the serialized list so it is editable in the Inspector. One toggle: `addDefaultPacks`. Context menu: "Add Missing Default Packs". Older saved data is upgraded by `MigrateOldPackData()`. It also removes a leftover "Pong" pack (name or minigame id `pong`) from the saved list and renumbers the other packs' requirements.

## Active conventions
- **Every variable must be editable in Unity**: `[SerializeField] private` + `[Tooltip]` (+ `[Header]` grouping). Nested config classes are `[Serializable]`.
- Static game state must be cleared on Restart: register the reset with `PixelStatics.ResetOnRestart` (statics outlive the scene reload; instance flags cleared in OnDestroy are fine). Look up the game's single components with `PixelFind.Cached<T>()` anywhere that runs often (`First` searches the whole scene every call); check 'in a menu' with `PixelCalm.InMenu`, not the pause / title flags by hand. Read / write settings through `PixelPrefs`, never `PlayerPrefs` directly; a new per-save setting calls `PixelPrefs.DeclarePerSave` with its kind. A new system component goes in the `PixelSystems.All` list (never another AddComponent line in Awake), sits in a file of the same name, and finds PixelClicker with a PixelFind fallback so it works on any object.
- Field initializers don't apply to already-serialized components → use Awake/OnValidate fix-ups for new defaults. No native-object constructors (`new RectOffset`) in field initializers.
- Version guards: `FindFirstObjectByType` vs `FindObjectOfType` (`UNITY_2023_1_OR_NEWER`); `PhysicsMaterial`/`linearDamping` vs `PhysicMaterial`/`drag` (`UNITY_6000_0_OR_NEWER`); `InputSystemUIInputModule` vs `StandaloneInputModule` (`ENABLE_INPUT_SYSTEM && !ENABLE_LEGACY_INPUT_MANAGER`). Input must work with both legacy and new Input System.
- UI is code-built: ScreenSpaceOverlay Canvas + CanvasScaler (1920×1080 ref, match 0.5) + GraphicRaycaster; auto-create EventSystem if missing; TextMeshProUGUI only. **One shared font** via `PixelClicker.UIFont`; every UI script applies it. Avoid obsolete TMP properties (`enableWordWrapping`).
- UI layout: line pitch ≥ 1.3× font size, header height computed from font; the Inventory and Log boxes have a centred title and a close "X" in a header above the tabs (clicking their button also toggles); titles capitalised ("Currency", "Log", "Shop").
- Clicks on UI must not hit the pixel (`EventSystem.IsPointerOverGameObject`); pixel hitbox is a full-size trigger so rapid clicks during materialize aren't lost; use `Physics.RaycastAll` with `QueryTriggerInteraction.Collide`.
- Scripts depend on each other (`FormatNumber`, `VacuumBreakdown`, `UIFont`, …). **Always copy the whole `Assets/Scripts` folder together** – most past compile errors (CS0122, CS1061, CS0246, CS0111) were stale/mismatched copies in the Unity project.
- **Compile check before committing:** run `tools/compile-check/check.sh` (compiles `Assets/Scripts` without Unity and checks the project rules in `rules.sh`, e.g. buttons only via `PixelUIKit.CreateButton` / `MakeClickable`; details in `tools/compile-check/README.md`) and fix every error it reports. It does not replace testing in Unity (editor-only / Unity-6-only / UI-TMP-stub gaps, run-time bugs).
- **Look for an existing helper before writing one (standing instruction from the user):** before writing code for a common job (UI pieces like one-line labels / buttons / info badges / tooltips, finding husks near a point, 'is this skill training', reading prefs, finding components...), search for a helper that already does it (`grep` PixelUIKit, PixelHuskQuery, PixelSkills, PixelCalm, PixelFind, PixelPrefs, the index above) and use it. Never paste a private copy of a helper into another script; if the helper is missing something, extend it in its one place.
- **Pinned sessions (standing instruction from the user):** the user keeps long-lived, pinned sessions, one per area, always with these names, to build up memory of recent work there. A session's area is given by its name (the user says it at the start, e.g. "This session will be for UI and interfaces"):
  - **Overview** - the whole game at once: status, priorities, planning across areas, what to do next.
  - **Design Discussion** - game design talk and decisions (mechanics, balance, progression, new ideas), mostly no code.
  - **Code Cleanup** - refactors, shared systems, performance, the compile check / tooling, docs organisation.
  - **UI and Interfaces** - PixelUIKit, windows, HUD, menus, tooltips, drop-downs / buttons, the title and pause screens.
  - **Console Errors** - errors and warnings from the Unity console or compile check, crash logs, run-time bugs.
  - **Cosmetic Elements** - looks: floors, skies, filters, block looks, effects, pet outfits, Look Studio.
  - **Skills** - the Skills window, skill packs, gathering skills, perks, trees, Mastery, XP.
  - **Shops** - the Shop, packs, upgrades, Operation, consumables, vendors' wares and prices.
  - **Devices** - husk machines and devices: Recycler, Storage Crate, Quantum Organizer, Funnel, Magnet, Fan, Vacuum, Sorters, Sprinkler, attuned devices, zone effects, the tester factory (conveyors, kiln, elevator, splitter, robot...).
  - **Husks and Physics** - how husks (and pets) move and feel: falling, bouncing, tumbling and settling, Pixel Grabbing (grab / throw), carrying in first person, the floor cap and lifetime, physics materials and weights.
  - **Gameplay Logs** - analysing the session recorder reports (`PixelSessionRecorder`) the user records while playing: pace, income / XP per minute, milestones, husk counts, and the balance changes they point to. Commits from this session go straight to the default branch.
  - When a topic fits two, a feature's own session owns how it WORKS (a skill's perk -> Skills, a shop item -> Shops, a machine's behaviour -> Devices, how a husk itself moves -> Husks and Physics) and UI and Interfaces owns how windows LOOK and behave in general; one-off bugs go to Console Errors.
- **Suggest the right session (standing instruction from the user):** do NOT suggest a new chat because a session has grown long or covered several features. When a request falls outside this session's area, still help if it is small, and say in one line at the end which pinned session it belongs in ("this fits the **Skills** session"), or, when none fits, suggest a new session with a short name for it. When the chat has been compressed (summarised), say so ONCE in the next reply (one line, e.g. "Note: earlier parts of this chat were compressed into a summary"). Either way, write decisions from the chat into the notes / to-do, since other sessions can't see this chat.
- Git: develop on the branch the session names (recently `claude/intelligent-cori-y2qt3d`); commit + push when work is done; no PRs unless asked.

- **The user never edits the code (standing instruction from the user):** Claude writes and maintains all of it; the user only tests in Unity and edits Inspector values / the Resources text files. Judge code cleanups FIRST by what helps Claude work safely across sessions (finding things, the compile check catching mistakes, one place per rule). The user does read the code now and then to learn, so keep it readable and explained (plain comments, clear names) - just not at the cost of the first goal.
- **Naming: the pixels that drop off the cube are called HUSKS (standing instruction from the user).** Use "husk(s)" in every player-facing text and in docs from now on, not "old pixel(s)". Code names keep the old wording (OldPixelInfo, oldPixels, OldPixelDespawn...) so nothing breaks; older texts still saying "old pixel" are to be renamed.
- **Save compatibility is not a concern during development (standing instruction from the user):** nobody tests old saves, so do not plan save migrations, keep code only for old saves, or warn about breaking saves. Still append new enum values at the end (Unity stores enums as numbers in the scene and Inspector).
- **Skill packs (Mining, Farming, Electrician, future ones) are chosen in the Skills window only - never add a switch for one to the Toggles window.**

## Big-picture check on every new feature (standing instruction from the user)
- Features like new pixel packs, skills, minigames or devices tend to be added one at a time with no shared system behind them, and the code turns into a mess nobody asked to clean up. **Before building a new feature, and again when reporting it, look at how it fits the game as a whole:**
  - Is there already a system for this kind of thing (a table, base class, helper, data-driven list)? Use it. If the new feature is the 3rd or later of its kind and each one is hand-wired, say so and propose the shared system instead of copying the pattern again.
  - Does it duplicate logic that lives elsewhere, add another scattered check (`Showing`, `IsPaused`, `TakeoverActive`...), or touch many files for one addition? Name it.
  - Is there an obvious performance cost (per-frame work, allocations, `Find` calls, unpooled spawns)? Avoid it or flag it.
  - Does it interact with saves, the Toggles / Skills windows, the shop, achievements or the database in a way that needs a migration or index update?
- In the reply, add a short **'Fits the game / could be better'** note: what the feature reuses, what it hand-wires, and the one or two cleanups worth doing. Keep it to a few lines.
- Small tweaks and bug fixes need no note. For a bigger refactor than the request, don't do it unasked: ask whether to build it now or add it to the to-do (see below).

## How the notes are organised (keep CLAUDE.md small)
- This file holds the working rules, the game-at-a-glance overview and the data model. The index (ONE line per script / system) lives in `docs/Index.md`.
- A new script / system: add its line to `docs/Index.md`, and a word or two to its group in 'The game at a glance' above (keep that section short - names, not details).
- Per-system detail lives in the **header comment at the top of the script itself** (short notes) or in **`docs/systems/<Name>.md`** (long ones: shop, skills, floors, skies, pets, vendors...). Open the doc / script header before changing a system.
- When you change a system: update its script header comment or its `docs/systems` file, and only touch its index line in `docs/Index.md` (and the overview) if what the system IS changed. Do not paste feature history into this file.
- **Ideas doc (standing instruction from the user):** loose 'maybe someday' ideas go in `Assets/Resources/Ideas.txt` (shown in Dev Hub > Docs > Ideas; '#' headings, '- ' bullets): add a line when an idea comes up that isn't on the to-do, and move it to `Todo.txt` when the user decides to build it. Older background notes (balance decisions, reworks, profiling) are in `docs/systems/OlderNotes.md`. The to-do list stays in `Assets/Resources/Todo.txt`.
